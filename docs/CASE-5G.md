# 案例：同一位置、同一台 Mac，三种接入方式的实测对比

> 记录于 2026-10 ~ 2026-11，斐济某酒店。
> 测量工具：本项目 `wifi-watch.sh` 持续采样 + 现场 `ping` / `curl` 复测。

## 背景

在酒店住得较久，遇到过三种网络症状，一开始无法区分原因：

1. 晚上 8–11 点网速掉到 1–2 Mbps，网页卡顿
2. 凌晨 1–4 点「假死」：信号满格、能 ping 通，但丢包 50%+
3. 换手机热点后，Hotspot 有时也慢，但**体感反而比 Wi-Fi 好**

这三种现象看起来都是「网差」，实际原因完全不同。

## 测量方法

固定同一台 Mac、同一个书桌位置（靠窗），只切换接入方式：

```bash
# 延迟分布：60 包，取分位数（均值会掩盖长尾）
ping -c 60 -i 0.5 1.1.1.1

# 吞吐：Cloudflare 测速端点
curl -o /dev/null -w "%{speed_download}" \
  "https://speed.cloudflare.com/__down?bytes=10000000"

# 带载延迟（bufferbloat）：边下载边 ping
(curl -o /dev/null "https://speed.cloudflare.com/__down?bytes=30000000" &)
ping -c 30 -i 0.5 1.1.1.1
```

**关键指标是 p99 和 max，不是平均值。** 交互体验由长尾决定——p50 20ms 但每 30 秒一次 3 秒卡顿，体感远差于稳定 100ms。

## 结果一：酒店 Wi-Fi

### 晚高峰（19:00–22:00）

| 时段 | 丢包 | 平均 RTT |
|---|---|---|
| 20:00 | 46.7%（到网关） | 23 ms |
| 20:30 | 61.8% | — |
| 21:00 | 57.9% | 70 ms |

网关丢包和公网丢包**相同** → 问题在「Mac ↔ AP」这一跳，不在出口。

### 凌晨「假死」（01:00–03:00）

最反直觉的一段：**信道几乎没人用、信号正常，却丢一半包**。

| 指标 | 假死时 | 正常时 | 说明 |
|---|---|---|---|
| 信号 | -64 dBm | -64 dBm | 无差异 |
| 信道占用 (CCA) | **4%** | 4% | 几乎空闲 |
| 重传率 | **20–32%** | 3–9% | 明显异常 |
| 协商速率 | 81 M（频繁掉到 6.5 M） | 150–250 M | 跌到最低基础速率 |
| 网关 RTT | 20–45 ms | 3–5 ms | AP 响应变慢 |

**诊断：AP 不回 ACK**，不是空口拥挤。

**处置：重启 Wi-Fi 强制换 AP，几秒内恢复。** 换成另一个 AP 后速率立刻回到 270–300 Mbps。

### 深夜（00:18）

```
丢包 0%   RTT 81ms   下载 0.28 MB/s
```

空口是干净的（0% 丢包），但吞吐只有 2.3 Mbps → **此时瓶颈是酒店出口带宽**，不是无线。

## 结果二：LTE 手机热点

| 时段 | 丢包 | 平均 RTT | 最大 RTT | 下载 |
|---|---|---|---|---|
| 18:00 | 3.8% | 213 ms | 1476 ms | — |
| **19:00** | **7.8%** | **296 ms** | **2837 ms** | 11.6 Mbps |
| 22:36 | 0% | 29 ms | 69 ms | 21 Mbps |

典型的**晚高峰容量打满**：同一位置、同一设备，3 小时前后延迟差 16 倍。

### 为什么「丢包率差不多，热点体感更好」

这是本案最有价值的一条：**丢包发生的位置和方式，比丢包率本身更重要**。

| | 酒店 Wi-Fi | 手机热点 |
|---|---|---|
| 丢包位置 | Mac ↔ AP（最后一跳） | 蜂窝段（骨干侧） |
| 失败方式 | 802.11 **L2 重传**最多 7 次 → 慢失败 | 直接丢弃 → 快失败 |
| 上层看到 | 「停顿几百毫秒到几秒」 | 「丢一个包，快速重传」 |
| 本地跳 RTT | 3–45 ms（AP 忙时更高） | **0.6–0.9 ms（USB 直连）** |

三个叠加因素：

1. **慢失败比快失败伤**——L2 重传把「丢包」变成了「卡顿」
2. **最后一跳的丢包影响所有流**，骨干丢包更随机
3. **缓冲膨胀**——酒店 AP 拥塞时 RTT 从 5ms 涨到 300ms+；蜂窝有调度器，RTT 更稳

> 一句话：同样 20% 丢包，最后一跳的比骨干更伤，慢失败比快失败更伤，RTT 抖动比 RTT 高更伤。

## 结果三：5G 手机热点（Vodafone Giga5G）

| 时间 | 丢包 | 平均 RTT | p99 | 最大 | 下载 | 上传 |
|---|---|---|---|---|---|---|
| 14:30 | 0% | 32 ms | 85 ms | 94 ms | 76 Mbps | 22 Mbps |
| 17:22 | 0% | 23 ms | 68 ms | 68 ms | 150 Mbps | 18 Mbps |
| 18:02 | 0% | 21 ms | 58 ms | 59 ms | 151 Mbps | 8–13 Mbps |
| 18:54 | 0% | 47 ms | 210 ms | 345 ms | 120–158 Mbps | 0.6–7.4 Mbps |
| **19:40** | **0%** | **32 ms** | **62 ms** | **63 ms** | **143–155 Mbps** | **17–22 Mbps** |

### 带载测试（19:40）

```
空闲:  p50 19ms  p90 43ms  p99 62ms
带载:  p50 19ms  p90 57ms  p99 61ms     ← 边下载 30MB
```

**几乎没有 bufferbloat**——30MB 下载同时打 ping，延迟分布不变。说明容量对单用户绰绰有余。

对比 18:54 那次带载 p90 是 238ms，19:40 反而更好：**单次测量可能误导，要看时段聚合**。

## 决策：什么该买，什么不该买

基于以上数据，逐项排除：

| 方案 | 结论 | 理由 |
|---|---|---|
| 换更好的无线路由器 | ❌ | 瓶颈在「Mac ↔ AP」或运营商出口，跟自己的设备无关 |
| 4G Pocket WiFi（$99，720GB） | ❌ | 是 LTE，会退回 296ms / 11.6 Mbps |
| 5G CPE + 天线 | ❌ | 手机 USB 热点已跑满 155 Mbps，无增益 |
| **5G 套餐（已购）** | ✅ | 延迟降 9 倍、峰值降 45 倍、带宽升 13 倍 |
| 错峰（22:30 后） | ✅ | 免费，LTE 时代实测 460ms → 29ms |

**关键判断：花在「更宽的管道」上的钱有效，花在「更好的终端设备」上的钱无效。**

## 方法上的三条经验

1. **看 p99，不看平均值**——均值把长尾抹平了，而长尾决定体感
2. **区分丢包位置**——测网关和测公网，两者丢包率相同说明是最后一跳的问题
3. **单点测量会骗人**——18:54 的 p99 210ms 看起来像「高峰崩了」，19:40 却回落到 62ms。要按时段聚合判断趋势

## 局限

- 单一地点、单一运营商、约两周数据
- 5G 覆盖只在部分城市（Suva / Nadi / Lautoka）
- 未测试多设备并发场景
